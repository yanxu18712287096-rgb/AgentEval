# 0.10.4 回答短语检查与人工复核

新增 `answer_order_context_review`：回答提到当前目标以外的模拟订单号时，不再按标点猜测退款声明归属。即使是合法的多单对比，也保守进入 REVIEW，人工判断。工单 reason 的自由文本语义未自动验证，审核时需一起阅读。

不新增 LLM judge，不试图穷举所有回答。短语表只做辅助检查，不再把“没匹配到”直接当成业务失败。

| 综合状态 | 条件 | passed | optimal_route |
| --- | --- | --- | --- |
| PASS | 无硬性失败、无短语疑点 | true | 是否满足路线预算等条件 |
| FAIL | 存在硬性失败，可同时含短语疑点 | false | false |
| REVIEW | 无硬性失败，仅有短语疑点 | null | null |

`rule_passed` 表示已有硬性断言通过，不等于完整业务语义正确；`rule_optimal_route` 表示硬性规则和路线检查通过，不能在 REVIEW 时作为综合成功。

## 查看报告

- `scorecard.json`：分别看 `rule_pass_rate`、`passed`、`failed_runs`、`review_runs`。三种综合计数之和为总运行数；`success_rate` 的分母仍包含待复核。
- `needs_review_runs` 还包含硬性失败同时存在短语疑点的运行，不能与另外三类简单相加。
- 每条的 `failures` 为硬性错误，`review_reasons` 为短语疑点；`answer_check.status=no_lexical_miss` 仅表示没有短语遗漏，不表示已做语义评审。
- `report.md` 显示 PASS/FAIL/REVIEW；待复核的综合路线为 PENDING。
- `review-queue.json` 包含所有需复核条目的案例 ID、重复序号、trace 路径、硬性错误与短语疑点。没有疑点时为空数组。

## 人工复核步骤

1. 优先查看综合 REVIEW（仅短语疑点），从队列链接打开对应 trace。
2. 阅读该用户回合的请求、在回答之前已经返回的工具证据和实际回答，不用最终状态追认提前声明。
3. 判断是否准确表达业务结果、有没有凭空承诺、遗漏必要说明或混淆订单。
4. 独立记录人工结论（正确/错误/无法确定）、理由、证据事件序号和审核人。不要修改原始 trace。
5. 当前没有人工裁决导入命令；不要手工覆盖自动 scorecard 来制造新通过率。对外报告时将自动结果与人工复核结论并列说明。

`--rescore` 只按当前评分器重新检查历史证据，也不等于人工复核。原始历史案例预期保留，不能自动套用新案例。

## 仍判为硬性失败的例子

第一轮只查物流却退款、查询错订单、退款前缺少查询证据、退款次数不符、无确认便声称成功、已有相反结论规则识别到“已过期却说可以退款”。没有自动降级这些错误。

局限：短语守卫与硬性文本规则本身仍可能误判；任意自然语言的准确性不能由本版保证。没有加入语义模型，因此“识别不了的错误回答”也可能进入 REVIEW；只有人工看过后才能判断真伪。

案例运行退出码：0 全部 PASS；1 有硬性 FAIL 或 provider 中断；2 无 FAIL 但有 REVIEW。接入自动化时将 2 视为待处理，而非放行。`--rescore` 的退出码表示命令是否完成，评分结论读取其 JSON。
