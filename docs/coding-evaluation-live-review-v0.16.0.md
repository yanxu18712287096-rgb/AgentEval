## 原始 3 个 FAIL 的原因

- `CODE-03` 重复 0、1：原隐藏测试要求处理双引号转义，但 issue 只要求处理引号内逗号。该断言越出需求，已替换为另一条引号内逗号用例；保留旧 trace 和旧分数，修正后对保存补丁重测均通过。
- `CODE-05` 重复 0：模型一次 `edit_file` 因旧字符串不匹配失败，随后修正了调用，最终补丁与公开/隐藏测试均通过。原评分器把任意工具失败都作为任务失败；新版将已恢复错误记为 `tool_error_count=1` 和效率告警，不抵消客观任务成功。该案例属于 holdout，因人工查看过其轨迹，此后**不能再称为未触碰的盲测集**。

先前一次无统一限速的 8×3 尝试在第 1 条第 7 次模型请求遇到 `RateLimitError`，报告 `complete=false`，未计入上述 24 次。更早的 CODE-01 单例 smoke 客观测试通过，但也不计入正式基线。

## 可以与不可以得出的结论

可以说：容器化工作区、模型工具轨迹、补丁产物、独立测试、严格指纹与历史产物重评分构成了可复核闭环；评分器缺陷可以通过原始证据被发现并修正，不必为了改分重新调用模型。

不能说：这个 Agent 在大型仓库 coding 任务上达到 100% 成功，也不能说 Skill、checkpoint 或异步子 Agent 已提高成功率。8 条任务都是微型合成缺陷，公开测试简单；修正过程中看过 holdout，后续若要证明泛化，必须冻结新的、真正未查看的仓库级案例。答案语义尚未由独立人工或校准的 Judge 完成复核。
