模型为环境配置的 `kimi-k2.7-code`，`temperature=1`，每轮输出上限 4096 token；无 Skill。

## 失败复核

- `REPO-D03 #0`：模型修改了服务和账本，公开测试通过，但 `stock.take()` 在先扣第一个 SKU、再发现第二个不足时留下部分扣减。验收 `test_R1_atomic_failure` 失败。公开 R1 已要求失败时库存与预留记录保持不变。
- `REPO-D03 #2`：同一原子性验收再次失败。最终回答还称 `Stock.take` 本身已原子化，而补丁未修改该函数；因此这次不仅有代码失败，也有回答事实不准确。
- `REPO-D03 #1`：原评分只因新增 `test_r1_r4.py` 报 `out_of_scope_change`；公开和隐藏测试均通过。任务要求不得修改已有测试，并未禁止新增自测文件。评分器现仅允许新增 `test_*.py`，仍拒绝修改已有测试或其他越界文件。以保存补丁在容器中重新运行当前测试后，此次客观通过。

因此原始 [scorecard](../eval/runs/repository-dev-calibration-20261001/scorecard.json) 保持 **6/9** 不变。
新的 [历史补丁复验报告](../eval/runs/repository-dev-baseline-rescore-v3-20261001/scorecard.json) 是 **7/9**，包含源报告 SHA、源产物哈希、当前评分器版本和重新执行的测试结果；它**没有新模型请求**，不能写作新策略实验。
基于复验报告提取的 [失败证据包](../eval/runs/repository-dev-baseline-rescore-v3-20261001/evidence.json) 经原始运行与当前评分器再次核查，只纳入 D03 #0、#2 两条业务失败。

## 难度判断与后续使用

首轮是 2/3 客观通过，重复运行后统一口径为 7/9：当前开发集并非全过，库存的批量原子性遗漏在两次独立运行中出现。
配置与队列均 3/3 通过，难以用它们证明正确率改进，但可作为回归与成本检查。任务均为 45–84 行左右的合成小仓库；两个库存失败来自同一需求，并不代表覆盖了多个独立失败模式。

目前**没有候选 Skill，也没有自进化效果数据**。下一步应人工核对 D03 #0/#2 的 trace 与根因，确认属于可推广的执行策略问题，再用这两条证据生成策略假设；候选形成后，在同一当前代码/评分器版本下新旧策略成对重跑。
旧运行指纹中的 Runtime 代码哈希与修正评分规则后的代码不同，不能把本次历史补丁复验值直接当作未来候选臂的严格对照基线。
留出集未用于本轮模型调用或提炼，但作者在案例编写与审计时已接触，不能称为第三方盲测。

最终校验：含 Docker 的全项目回归 `RUN_DOCKER_CODING_TESTS=1 venv311/bin/python -m pytest -q` 为 **522 passed**。证据包来源于当前复验评分器再次重测 9 份原始产物；只容忍 `unittest` 输出中的耗时数值变化，其余测试状态、输出、来源哈希必须一致。
