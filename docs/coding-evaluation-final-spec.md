# Coding Agent 评测闭环：目标规格与 v0.16.0 实现边界

状态：这是更大范围的目标规格，并非 v0.16.0 的已交付清单。面试展示版已完成的能力及刻意不做的边界以 [v0.16.0 交付说明](coding-evaluation-v0.16.0.md) 为准。不得将微型合成案例称为大型任务基准。目标是扩展现有 Harness，而不是把 CoreCoder 改造成 XiaoBa-CLI 的跨设备产品。

## 定位与范围

保留订单客服作为强规则工具场景；新增 coding 任务作为真实产物场景。第一被测对象为本项目自身的 CoreCoder Agent。外部 Agent 只能通过明确的适配器协议接入，不假定不同 Agent 的内部 trace 格式相同。

目标版本以“可安全运行、可重复评分、可解释退步”为完成条件，而非以功能清单或固定通过率为完成条件。不实现跨设备路由、Electron、多聊天渠道、自动发布 Skill 或自动修改评分标准。

## 必须交付的闭环

1. **案例**：至少 8 个经过人工审查的 coding 任务，覆盖单文件错误、跨文件修改、边界条件、回归风险、错误测试线索和长上下文。开发集与冻结 holdout 分开；案例包含固定仓库快照、用户 issue、允许修改范围、公开检查和隐藏检查。隐藏检查不暴露给被测 Agent。
2. **执行隔离（目标）**：每次运行从只读快照创建全新工作区；若面向不可信代码，Agent 及其工具应在容器或等效 OS 沙箱内运行。v0.16.0 实际仅把 Shell/测试放入容器，Agent 及受路径限制的文件工具仍在宿主进程，详见已交付边界。没有可用隔离后端时拒绝运行 live coding 评测，不能降级为直接在宿主机执行 Shell。
3. **证据**：保留原始模型/工具 trace、初始快照哈希、最终补丁、公开/隐藏测试原始输出及退出码、运行环境标识、耗时和 token 使用情况。模型可见上下文压缩不改写原始证据；工具调用与结果按 ID 配对。
4. **评分**：硬性检查包括隐藏测试、既有测试、改动范围和执行完成性；单独报告补丁质量、测试执行轨迹、最终陈述是否被证据支持、工具/模型成本。硬性失败不能被 LLM Judge 或人工语义裁定改成通过。语义争议进入 REVIEW，并记录裁定者与证据定位。
5. **回归**：同一案例、快照、测试、模型参数、Role/Skill 和评分器版本严格比较；有意改变候选版本时使用受控配对实验。历史 trace 重评分与重新执行分别标注。每例至少重复 3 次，报告成功率、退步/改善案例、离散度、token、工具次数和耗时。缺 holdout 或 REVIEW 未裁定时不声称总体改进。
6. **可复核交付**：一条命令验证环境与案例；一条命令运行开发集；一条命令运行冻结集；输出机器可读 scorecard、人工可读报告和每例证据索引。文档给出失败复现步骤、运行费用预估方法及安全边界。

## Runtime 必要改造

- 抽象被测 Agent 适配器：输入 issue 与工作区，输出执行终态和标准事件；第一版实现 CoreCoder 适配器，不伪称已支持任意外部 Agent。
- 为 coding 工具建立案例级工作区边界。并行工具各自保留线程状态，但写同一文件、Shell 与编辑器的并发冲突必须串行化或明确拒绝；不得以线程局部 cwd 代替文件系统隔离。
- 检查点只在完整工具批次之后提交；恢复时重新验证文件、进程和未完成工具的状态。中断前的副作用状态为 unknown，不自动重放非幂等操作。
- 子 Agent 异步化并非第一版硬门槛。若引入，分支上下文、工具、日志和取消信号必须隔离，结果以有生命周期的 observation 返回，并针对迟到、重复和无价值注入评分。

## 验收门槛

- 单元/集成测试证明不同案例及重复运行之间的文件、进程和结果互不污染。
- 故障注入覆盖测试超时、容器失败、模型中断、重复运行、结果缺失、工具 ID 错配与非法越界写入；失败应有明确分类，不吞成普通模型失败。
- scripted 模式只验证评测管线；live 模式必须使用真实模型并保留完整证据。两者不得混算通过率。
- 至少一轮冻结开发集基线和一轮 holdout 测试完成，结果经过人工抽查；若无真实模型额度或隔离后端，本规格保持未完成。

## 当前项目可复用与缺口

可复用 `ScenarioSpec`、`TraceRecorder`、版本指纹、`rescore_trace`、严格比较与配对实验。当前 `state_factory` 只保证内存业务状态独立，不保证任意 Shell 命令的宿主机隔离；现有 Session 保存也不是完整 coding 执行 checkpoint。订单场景 38 条案例均为 development，不能直接作为 coding 场景 holdout。

## 与 XiaoBa-CLI 的关系

参考其长任务 checkpoint 的稳定边界及 Branch Session 的独立上下文/临时 observation 思路；不复制跨设备执行产品形态，也不把其 Runtime 测试误称为现成 coding 基准。参考：<https://github.com/buildsense-ai/XiaoBa-CLI/blob/main/docs/checkpoint-compaction-v2.md>、<https://github.com/buildsense-ai/XiaoBa-CLI/blob/main/docs/branch-session-architecture.md>。
