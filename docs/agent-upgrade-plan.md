# CoreCoder 垂直场景升级方案（讨论稿）

文档版本：`0.4` · 2026-09-28  
原项目代码基线：CoreCoder `0.7.0`；当前本地版本：`0.9.2`（见 `pyproject.toml` 和 `corecoder/__init__.py`）  
状态：本地代码已升级至 `0.9.2`，第 9 节保留升级前的方案与问题定义作为决策记录；实现和验证见 [使用说明](evaluation-guide.md) 与 [升级记录](agent-upgrade-changelog.md)。真实模型 40×3 次运行已完成，但 [审计](live-evaluation-audit-v0.9.2.md) 发现案例和字面断言缺陷，需用户审查修订后才能形成可信基线。前文保留 `0.7.0 → 0.8.0` 的历史基线与设计动机。

## 1. 为什么做

本项目的目的，是展示 AI 应用开发中的工程判断与验证能力。CoreCoder 原项目提供可读、可改的 Agent 内核；在此基础上，选择“订单客服的工具调用回归测试”作为受控场景，验证模型、提示词或工具 schema 改动后，Agent 是否仍按业务规则调用工具、处理异常并给出可信回答。

目标用户是开发工具调用型 AI 应用的工程师。交付物是一条可重复的工作流：**定义案例 → 运行 Agent → 保存完整 trace → 程序化判分 → 与基线比较失败案例**。本项目不以通用编程能力超过 Codex 或 Claude Code 为目标；垂直场景的优势需要由回归数据证明，不能仅凭功能数量宣称。

面试时必须区分原项目能力与个人新增能力。CoreCoder 原作者及原项目来源保留在现有 README 和包元数据中；简历与演示应明确说明哪些部分是在其基础上设计、实现和评测的。

## 2. 当前基线与缺口

| 能力 | `0.7.0` 现状 | 本方案中的处理 |
| --- | --- | --- |
| Agent 主循环与工具接口 | `corecoder/agent.py` 已支持自定义工具列表；`corecoder/tools/base.py` 定义工具 schema 与 `execute` | 复用，不重写主循环 |
| Role / 系统提示词 | `corecoder/prompt.py` 固定为编程助手 | 增加可注入的客服 Role；默认仍使用原提示词 |
| 工具执行 | 单个工具同步执行，同轮多个工具走线程池 | 复用执行机制；同轮并发不能被误判为先查询、后退款 |
| 权限与 Hooks | 已实现；`Permission.READ_ONLY` 按工具名硬编码 | 评测环境只装模拟工具；退款的业务约束放在工具中，不依赖提示词或 Hook |
| 会话与上下文压缩 | `session.py` 保存消息；`context.py` 会裁剪历史 | 另建不可被压缩的评测 trace，不把会话消息当完整证据 |
| 子 Agent、MCP、Plan 模式 | 均有基础实现 | 第一阶段不依赖，也不重复建设 |
| 订单案例 | `eval/cases/examples.json` 有 3 条格式示例 | 补足已审核案例，建立可执行断言 |
| 回放与评分 | 尚无 | 本方案的主要新增能力 |

## 3. 第一版的边界

只测试三个模拟工具：`query_order`、`query_tracking`、`refund_order`。每条案例有独立的订单 fixture，运行时复制数据，禁止案例之间共享可变订单状态。第一版不接真实订单系统，也不处理真实个人信息。

Role 规定客服任务、工具用法和回答原则；业务规则由工具及评分器共同保证。例如，`refund_order` 必须检查订单状态和重复退款，评分器则检查 Agent 是否先取得查询结果、是否产生意外退款。Skill 可在形成稳定诊断流程后加入，不能代替可执行断言。

第一版先完成 10 条人工审核的核心案例，覆盖正常查询、缺失订单号、不可退款、重复退款、工具失败和用户改变意图。运行与评分稳定后，再扩充到约 30 条输入变体；数量不是验收标准。

## 4. 拟议实施顺序

### 阶段 A：客服 Agent 最小闭环

1. 为 `Agent` 增加可选系统提示词注入入口，保持既有调用方式兼容。
2. 实现三个模拟订单工具和案例级订单仓库；退款操作按订单状态拒绝或执行，记录实际副作用次数。
3. 从 `eval/cases/` 读取案例，每条案例使用新的 Agent、工具实例和订单 fixture；支持顺序输入多轮用户消息。

验收：离线模拟工具的单元测试覆盖订单不存在、已退款、重复调用和错误返回；客服 Agent 可以运行一条案例。此阶段不以模型回答好坏作通过标准。

### 阶段 B：完整 trace

1. 增加独立事件记录器，记录 `run_id`、`case_id`、模型与配置、输入、轮次、模型回复、每个 `tool_call_id` 的工具名/参数/结果/状态、最终回答、耗时和 token 用量。
2. 在 Agent 的工具执行边界记录事件；正常完成、拒绝、参数错误、工具异常、中断都应有对应结果。线程并行写入时保证事件完整，并区分调用发起、执行完成与结果回填的时序。
3. trace 以 JSONL 或 JSON 文件保存在 `eval/runs/`。不把原始完整 trace 塞回模型上下文；敏感值如密钥不得写入 trace。

验收：每个 `tool_call_id` 恰有一个最终结果；并发工具调用可追溯到各自结果；上下文压缩不改变已保存的 trace。被中断且未实际执行的工具明确标记，不把回填文本误写成执行成功。

### 阶段 C：回放、判分与基线对比

1. 回放器读取案例 fixture，**重新驱动当前版本 Agent**，产生新的 trace；旧 trace 只作为比较基准，不复用旧模型回答。
2. 评分器先实现确定性断言：必需/禁止工具、参数匹配、跨轮先后关系、实际退款次数、最终回答中的必要信息、调用与结果完整性。
3. 输出每条案例的失败原因与汇总分数；保留基线和候选版本的逐案例对比，不只展示总通过率。

验收：评分器自身用固定的人工构造 trace 测试，确认同轮并发的查询与退款不能通过“先查询再退款”断言；至少 10 条审核案例可以反复运行并生成报告。真实模型运行有随机性，比较时固定可控配置并保留多次运行结果，不把一次运行差异直接归因于代码改动。

### 阶段 D：由评测结果驱动的 Agent 改进（后续决定）

先分析失败分布，再选择具体改动。可能方向包括更清晰的客服 Skill、工具 schema、异常恢复、上下文保真或受控重试。只有当评测表明同步执行限制了目标场景，才考虑异步子 Agent 或多 Agent 协同。每项改动都需要在同一案例集上做前后对比，并保留失败案例。

## 5. 不变量与设计取舍

- **调用完整性**：用 `tool_call_id` 关联请求与最终结果；同名工具可在一轮调用多次，不能仅靠工具名配对。
- **上下文安全**：压缩时保留 assistant 的整批 `tool_calls` 与对应的全部 `tool` 回复；trace 独立于可压缩的 `messages`。
- **状态隔离**：每条评测案例有独立订单副本；并行工具访问同一订单时，由工具层保证一致性与退款幂等。
- **顺序真实性**：同轮并行发出的两个工具调用没有“查询完成后才退款”的因果关系；判断先后需要看轮次与完成事件。
- **评分可解释**：先用确定性业务断言；涉及回答语义的检查单独标记人工审核或模型评分，不与硬约束混成一个分数。
- **结果诚实**：报告案例集规模、模型配置、运行次数、通过率、失败原因和成本；不对未评测场景作泛化结论。

## 7. 版本与更新记录规则

原项目代码基线为 `0.7.0`；第一版本地实现为 `0.8.0`，两处版本字段已同步。本地版本号不代表已向 PyPI 或远端发布。后续新增兼容功能增加 minor 版本、兼容修复增加 patch 版本；不兼容变更单独说明迁移方式。文档或实验准备记录到 Unreleased，不凭规划提前提升代码版本。

以后**每次在原 Agent 基础上发布更新**，同一变更中必须更新 `docs/agent-upgrade-changelog.md`，记录：版本与日期、相对上一版的行为差异、新增/修改/移除内容、影响的文件与接口、回归案例和测试结果、已知限制、原项目能力与个人新增能力的边界。只修改文档或尚未完成的实验可记入 `Unreleased`，不得伪装成已发布能力。

发布前检查：代码版本一致；案例和评分报告可追溯；原有测试通过；新功能有对应验证；变更日志写清“之前怎样、现在怎样、为什么改、证据是什么”。版本模板见 `docs/agent-upgrade-changelog.md`。

## 9. v0.9.0 升级方案原稿（2026-09-28；离线闭环已实现）

### 9.1 核心问题与目标

升级前 `0.8.0` 的 `refund_order` 只检查订单是否存在、状态是否可退和是否重复退款，**没有在工具执行时校验“该订单已被成功查询”**。因此 Agent 直接调用退款工具时，对 `pending` 或 `delivered` 订单可能实际退款成功；评分器随后才会判定路径错误。此段是历史问题定义；`0.9.0` 的工具层凭据校验已实现。

下一版同时解决两个问题：

1. 工具执行前阻止缺少必要查询证据、订单不一致、重复或不符合政策的退款；实际错误副作用为零。
2. 在任务成功且安全的前提下，测量 Agent 是否绕路、被拒后重试或浪费模型轮次和 token，用评测结果指导 Role、Skill 和工具 schema 的改进。

场景从三工具演示扩展为售后决策流程。拟新增“按用户查订单、查支付状态、查退款政策、查退款进度、转人工”等能力，目标约 7～8 个工具；最终工具清单以案例确实需要的信息为准。订单、支付、物流和政策各自拥有独立 fixture，可出现缺失或相互矛盾的结果。涉及用户身份、政策期限和退款金额的具体规则，实施前需在案例说明中写清并经用户审核。

### 9.2 工具层兜底与可追溯拒绝

- `query_order` 成功后给同一订单生成**本次案例/会话绑定的查询凭据**。`refund_order` 要求该凭据及匹配的 `order_id`；工具验证凭据有效、订单/支付/政策状态、退款幂等，并在一次原子操作中修改模拟状态。同轮并发的退款无法预先得到该轮查询结果中的凭据。凭据只用于模拟业务流程，不宣称是生产级身份认证机制。
- 无凭据、凭据不匹配、状态不允许或已退款时，工具返回结构化 `ok=false` 和稳定错误码，不产生退款副作用。评分器同时记录违规**尝试**、工具**拒绝**和最终**实际退款次数**；成功完成任务也不能抹去中途的违规尝试。
- 对工具拒绝进行分类：`policy_rejected`（业务前置条件/政策/重复操作）、`permission_blocked`（权限或 Hook）、`invalid_arguments`（参数错误）。模拟超时、服务不可用属于 `transient_failure`，单独统计，不混入“后端拒绝违规调用”。只按明确的工具结果与执行状态分类，不靠最终回答猜测。
- 保持现有的 `tool_call_id` 与终态结果一一配对；并行调用在 trace 中保留发起、完成的真实顺序和轮次。

### 9.3 每条案例新增的效率指标

每次运行在现有正确性和安全断言之外记录：

| 指标 | 明确口径 |
| --- | --- |
| 模型轮次 | 当前案例所有用户回合内的主 Agent 模型请求总次数；压缩摘要等内部模型调用另计，不能隐匿 |
| 工具调用次数 | Agent 发起的工具调用总数，包含成功、拒绝、失败和超时；另列各工具及各结果状态次数 |
| 被拒绝调用次数 | `policy_rejected`、`permission_blocked`、`invalid_arguments` 分列；暂时故障另列 |
| token | 输入、输出及合计 token；主对话与内部摘要调用分列，同时给出可计算的总量。provider 缺失用量时标记 `usage_unavailable`，不当作 0 |
| 耗时 | 案例从首条输入开始至最终回答或失败的总墙钟时间；工具与模型耗时可另列；重复运行报告中位数与分布 |
| 业务结果 | 是否完成用户目标、是否出现错误退款副作用、回答是否与工具事实一致；人工或语义判定单独标注来源 |

trace 和 scorecard 增加上述字段及 schema 版本。历史 `0.8.0` trace 仍可阅读；缺失新字段时明确标记不可用于新效率指标的直接比较，不能补成 0。模型、Role、工具 schema、fixture、案例断言及运行参数需留有可追溯标识。

### 9.4 “最优路线案例 / 所有案例”的定义

这里的“最优”指**达到案例预先审核的高效路径标准**，不是数学上证明全局最优，也不要求只有唯一的工具调用序列。每条案例在运行前给出：用户目标、必要证据、允许的工具路径、`max_model_rounds`、`max_tool_calls`，以及例外情况（如预设工具故障允许一次重试）。不同但同样正确的路径应被允许；这些标准不能在看到候选模型输出后临时修改。

一条运行记作“最优路线达成”，必须同时满足：业务任务完成、没有错误副作用、没有不必要的业务拒绝调用、必要证据齐全、模型轮次和工具调用数都不超过该案例阈值。故障案例的预期重试不算绕路。token 与耗时在每条案例中展示，并报告整体分布及改善幅度；由于模型用量回传和网络时延可能不稳定，第一版**不把固定毫秒/token 阈值作为路线达成的硬门槛**，但不能据此忽略成本退化。

核心比率：`最优路线达成的案例运行数 / 全部案例运行数`。失败、超时、未完成、缺失必要证据的运行都留在分母；按每次运行计数，并同时报告“成功率”“成功案例中的高效路线占比”“平均/中位模型轮次、工具次数、token、耗时”和拒绝类型分布，避免一个比率掩盖问题。若每条案例重复运行 3 次，分母就是 `案例数 × 3`，不挑最好的一次。

### 9.5 案例设计与验证

- 先经用户审查模拟业务规则，再扩展至约 40 条案例。开发集与留出集分开；留出集不用于反复修改 Role/Skill。案例涵盖多订单歧义、支付与订单状态冲突、政策边界、重复退款、退款结果未知、工具超时/空结果、用户改变意图，以及不可信工具文本中的指令干扰。
- 每条案例同时验证最终任务结果、必要证据、错误副作用和调用效率。用反例测试证实：直接退款、同轮并发查询退款、A 订单凭据用于 B 订单、重复退款，实际退款次数均为 0，且拒绝分类和 trace 正确。
- 真实模型基线与候选版本应使用同一经审核的案例集、模型、采样参数与工具 fixture，至少重复 3 次，逐案例报告结果与波动。`scripted` 模式只验证执行/评分流程，不能用于声称模型效率提升。
- 如果工具接口或案例 schema 变化导致 `0.8.0` 不能运行同一套案例，报告必须注明不可直接横向比较；可在新 schema 下重建可运行的基线或只比较同一版评测器下的不同 Agent 配置，不拼接不兼容的通过率。

### 9.6 实施拆分与验收

1. **业务与案例设计**：先冻结模拟规则、工具输入输出和逐案例的高效路径阈值，由用户审查。产物是案例规范与至少一批手工审核的代表案例。
2. **工具约束与 trace**：实现凭据校验、状态原子更新、拒绝分类、主/内部模型调用计量和耗时记录；用并发与失败反例验证安全不变量。
3. **评分与真实基线**：扩展案例、回放和 scorecard，输出“最优路线案例/所有案例”占比及上述成本指标；在可用的真实模型配置下重复运行并保存原始 trace。
4. **针对失败改进 Agent**：只针对证实的错误模式调整 Role、Skill、工具说明或异常恢复；比较前后案例、拒绝调用、token 和耗时。若无法证明改善，记录未改善与原因，不宣称效率提升。

首版从已有 scorecard 提取结构化失败码与成本，生成候选 Skill 草案（可选调用模型），并以隔离的候选注册表执行同案例基线/候选成对试验。门槛校验版本指纹、三次重复、development/holdout、完整 token、REVIEW 复核、业务/路线/安全回退；只输出人工采纳建议，不自动修改生产 Skill。详见 [评测指南](evaluation-guide.md)。

当前订单 38 条均为开发集，历史错误码含规则误判；尚须新增、冻结独立 holdout，并建立 REVIEW 的独立语义复核流程后，才能评价真实模型改进。校园帮助场景暂时搁置；此框架在其他场景的可迁移性仍待实证，不能以通用接口代替业务验收。
