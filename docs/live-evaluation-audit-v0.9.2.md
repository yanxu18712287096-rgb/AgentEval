# v0.9.2 真实模型评测审计（案例复核已完成，处理见 [0.9.3 升级记录](agent-upgrade-changelog.md)）

> 本文是被审计的 **0.9.2 原始记录**，保留当时的发现与数字，不改写。下文的 5 项案例/评分缺陷已在 0.9.3（案例集修订 3）按用户逐项选定的情景修订，逐条对照见 [修订对照](#修订对照0-9-3)。修订后脚本演练 120/120，**但真实模型基线尚未重跑**，因此 49/120 与 29/120 仍是旧案例、旧断言下的原始分数。

本次使用 `kimi-k2.7-code` 运行 40 条模拟订单客服案例，每条独立重复 3 次。配置：`temperature=1`、`max_tokens=4096`、请求间隔至少 6 秒、provider 429 额外重试最多 2 次。运行目录为 `eval/runs/v0.9.2-kimi-live/`，含案例快照、逐次 JSONL trace、[报告](../eval/runs/v0.9.2-kimi-live/report.md)和[结构化评分](../eval/runs/v0.9.2-kimi-live/scorecard.json)。该目录被 `.gitignore` 忽略；需要共享时须导出脱敏证据。API key 和 endpoint 未写入报告。

## 原始指标

| 指标 | 结果 |
| --- | ---: |
| 计划 / 完成运行 | 120 / 120 |
| 任务断言通过 | 49 / 120 = 40.8% |
| 预设高效路线达成 | 29 / 120 = 24.2% |
| 在通过任务中路线达成 | 29 / 49 = 59.2% |
| 平均模型轮次 / 工具调用 | 3.425 / 3.225 |
| 平均 / 中位总耗时 | 66.479 / 60.902 秒 |
| 平均 / 中位观测 token | 2872.808 / 2842 |
| 工具成功 / 政策拒绝 / 模拟暂时故障 / 业务错误 | 346 / 13 / 22 / 6 |

所有 120 次均有 provider 返回的 token usage；14 次由完整 trace 恢复，其内部摘要调用用量无法独立从旧 trace 验证。每次耗时包含本地限速与重试等待，不能解读为模型纯推理时延。`transient_failure` 是案例注入的模拟故障，不等于 API 限流；本次无未完成的 provider 错误。异常退出码仅表示案例断言未全过。

## 必须先修的案例与评分问题

1. `query_fault_other_order`：用户要求退款 `A1002`，fixture 却只给 `query_order:Z404` 注入故障，离线脚本也查询 `Z404`，期望模型不退款并回答“未找到”。用户输入和断言不一致，不能拿该案例的 3 次失败评价模型。
2. `identity_list_filtered`：用户说“查询订单 A1002”，评分却要求必须调用 `list_user_orders`。实际模型调用 `query_order` 是合理路线；3 次 `missing_tool` 是案例设计错误。
3. `intent_change_1`～`3`：第一回合已明确“我想退 A1002”，第二回合才取消。按实时对话顺序，第一回合退款可能是当时被授权的；要求两回合结束时 `refund_count=0` 不成立。9 次运行须重设情境后重评，例如第一回合只询问退款条件，第二回合在真正退款前改变意图。
4. `final_answer_contains` 是严格子串匹配。33 次失败只由回答措辞触发；例如“退款已成功完成”不包含连续的“已完成”，却表达了相同业务结果。须在冻结案例前改为结构化结果与经审核的语义判断，不可事后为本次输出调阈值。
5. `policy_1`、部分 `in_transit_*` 案例把转人工判失败，但客服 Role 允许信息缺失/冲突时转人工。先统一 Role 与业务决策表，再重设路线预算。

## 修订对照（0.9.3）

用户逐项选定了情景；下列为实际改动，详细差异与验证见 [0.9.3 升级记录](agent-upgrade-changelog.md)。

| 审计条目 | 处理 |
| --- | --- |
| 1 `query_fault_other_order` | 重命名为 `refund_unknown_order`，用户改报不存在的 `Z404`，删除从未触发的 `query_order:Z404` 故障；断言只要求「查过订单、不得退款」，回答接受如实说明或请用户核对 |
| 2 `identity_list_filtered` | 话术改为「我有哪些订单？」，`A1002` 改属 U1、`B2001` 仍属 U2，使 `must_call: list_user_orders` 与「不得出现 B2001」同时可满足 |
| 3 `intent_change_1`～`3` | 第一回合改为「先确认能不能退」，第二回合在退款发生前取消；预算 5 轮 / 3 次调用 |
| 4 `final_answer_contains` | 换成 `final_answer_any` 同义词组，旧键名被 `validate_cases` 拒绝；能结构化的业务结果（退款次数、转人工次数、工具调用）继续只看结构 |
| 5 `policy_1` / `in_transit_*` | 统一决策表：缺失或矛盾必须转人工，明确不可退只说明并禁止转人工，暂时故障禁止转人工；Role 同步改写 |

另外清除了 3 组重复案例（`identity_3` 是 `identity_1` 的逐字复制、`query_fault_1`==`query_fault_2`、`uncertain_refund_1/2/3` 三条互相相同），改为不同行为变体，案例总数仍为 40（development 30 / holdout 10）。

## 值得继续调查的真实行为

- `policy_3`（签收后超过退款期限）3 次都调用了不应调用的 `refund_order`；工具返回政策拒绝，实际退款次数为 0。此例体现工具层兜底与 Agent 效率评测的区别。
- `uncertain_refund_3` 和 `refund_precommit_timeout` 中出现没有先 `query_refund_status` 就结束或继续操作的运行；需要逐条核对状态是否未知、是否真的需要重试。
- `clarify_1` 中模型列出唯一订单并请求确认，未猜测退款，但因没有说出“订单号”被判失败。它和真正“未澄清就退款”应分开标注。

案例审查已完成并形成 0.9.3（案例集修订 3）的冻结集；下一步是在相同模型、参数和重复次数下重跑基线。当前 **49/120 与 29/120 是原始评分器输出，不是经过案例审查的模型能力指标**；不要将其写成简历中的效果提升或与脚本 120/120 对比。0.9.3 修订了自己的 Role 表述与断言口径，因此新旧结果只能各自内部比较，不能拼成趋势。
