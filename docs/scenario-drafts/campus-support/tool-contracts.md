# 两个只读工具的契约

资料版本：0.2.0-draft；v0.12.0 已注册两个只读工具。无数据库、无业务写操作，也不加载通用文件或 Shell 工具。

## 公共约定

- 每个案例固定可信的 `as_of`（ISO 8601，含时区）；由运行器设置，模型不可更改。多轮如需推进时间，由案例逐轮设置非递减时间。
- 帮助资料和公告按案例快照加载；仅帮助条目和公告正文可检索，README、评分标准、参考答案和本契约不能成为检索资料。
- 成功外层结构：`{"ok":true,"as_of":"...","items":[]}`。空数组是正常无匹配，不是工具失败。
- 失败外层结构：`{"ok":false,"as_of":"...","error":{"code":"TIMEOUT","message":"查询超时","retryable":true}}`。失败无 `items`，不得视为无匹配。
- 错误码包括 `INVALID_ARGUMENT`、`FUTURE_TIME`、`TIMEOUT`、`DATA_UNAVAILABLE`。前两者不可原参数重试，后两者的 `retryable` 由故障配置确定。
- v0.12.1 的测试 fixture 可为工具设置 `"TIMEOUT"`（持续超时）或按合法调用消耗的序列，如 `["TIMEOUT", null]`（第一次超时，第二次恢复）；每个案例独立复制序列。这个配置仅属于评测环境，不暴露给被测 Agent。
- 未知字段、错误类型、无时区或非法日期必须拒绝，不自动纠正模型参数。调用/结果仍按 `tool_call_id` 一一对应写入 trace。
- 证据标识在冻结的语料快照内唯一。返回内容必须原样来自该快照；工具不根据案例标准答案拼装结果。

## search_help

输入：

```json
{"query":"PDF 上传 文件太大"}
```

`query` 为必填非空字符串，去除首尾空白后 1–200 字符，无其他参数。

返回示意（实际 `content` 返回完整命中条目，不截断）：

```json
{
  "ok": true,
  "as_of": "2026-09-28T09:20:00+08:00",
  "items": [{
    "evidence_id": "HELP-UPLOAD-001@0.2.0-draft",
    "document_id": "HELP-UPLOAD-001",
    "version": "0.2.0-draft",
    "title": "文件格式与大小",
    "effective_at": "2026-09-01T00:00:00+08:00",
    "content": "完整条目正文（此处仅为结构示意）"
  }]
}
```

首版可采用固定关键词/别名检索，不需要向量数据库。规则、别名和排序应版本化；返回全部命中的有效条目，按 document_id 排序。当前只有五条帮助资料，不设隐含截断。规则必须覆盖中英文常见称呼，但不得使用 case_id 选择答案。仅返回 `effective_at <= as_of` 的资料；无匹配返回空数组。

## search_service_notices

输入：

```json
{"service":"upload","occurred_at":"2026-09-28T09:15:00+08:00"}
```

- `service` 必填，枚举 `login` / `upload` / `report`。
- `occurred_at` 可选，表示用户问题发生时刻；省略表示询问案例当前时刻 `as_of`。晚于 `as_of` 返回 `FUTURE_TIME`，而不是允许读取未来资料。
- 时间不明确又会影响判断时由 Agent 追问，不把“发生时刻”误当“信息可见时刻”。

返回示意：

```json
{
  "ok": true,
  "as_of": "2026-09-28T09:20:00+08:00",
  "items": [{
    "evidence_id": "NOTICE-UPLOAD-001/U1@0.2.0-draft",
    "notice_id": "NOTICE-UPLOAD-001",
    "version": "0.2.0-draft",
    "service": "upload",
    "updates": [{
      "revision": "U1",
      "published_at": "2026-09-28T09:10:00+08:00",
      "status": "investigating",
      "started_at": "2026-09-28T09:00:00+08:00",
      "restored_at": null,
      "content": "该更新的完整正文（此处仅为结构示意）"
    }]
  }]
}
```

筛选顺序必须固定：

1. 先删除所有 `published_at > as_of` 的更新。禁止使用被删除更新的恢复时间参与筛选。
2. 对每个事件，以剩余更新中最新状态确定已知区间；未发布恢复消息时，结束时间视为未知。
3. 筛选服务匹配且 `occurred_at` 位于已知区间的事件；结束未知时只要求不早于开始。返回该事件全部可见更新，按发布时间排序，保留前版影响范围和症状。
4. `evidence_id` 使用最后一条可见 revision；数组按 notice_id 排序。多个事件均匹配时全部返回，不自行认定用户故障的原因。

在 09:42 查询上传事件时，09:45 发布的恢复消息仍不可见，即使事后知道服务于 09:40 恢复；此时只能说“截至已发布公告仍在调查”。在 10:00 查询 09:15 的问题时，可以返回 U1、U2，解释当时故障以及后来恢复。10:00 查询当前问题则不匹配该已结束事件。

返回匹配事件不等于已确定因果关系，Agent 还须核对报错和影响对象。没有匹配公告不代表服务健康。本工具不是实时监控接口。
